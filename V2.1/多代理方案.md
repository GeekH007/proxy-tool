## 一、目标与范围

**第一阶段（本次实现）：**

- 本机 HTTP 代理入口（透明转发、零协议解析），系统代理改指向它

- 故障切换：拨号失败顺延下一台，全挂才断客户端；简单熔断

**非目标（第一阶段明确不做）：**

- SOCKS5 上游（透明转发只认 HTTP 上游；91 若是别的协议再说）

## 二、核心设计（含两处修正）

### 2.1 入口 = 透明转发，不解析协议

初稿"只做 CONNECT"是错的：明文 `http://` 请求（绝对 URI 的 GET）不走 CONNECT，会漏。
正确做法更简单：**入口不解任何协议**——客户端连上入口后无论发 CONNECT 还是 GET，
字节原样转给选中的上游（上游本来就是 HTTP 代理，什么都认识）。
即 `HttpServer` ≈ `RelayServer` 克隆 + 上游池选择器，实现量比重写桥接更小。

### 2.2 监听地址：必须绑 127.0.0.1

RelayServer/SocksServer 绑 `0.0.0.0` 因为要给局域网用。入口只服务本机，
**绑 127.0.0.1**——绑 0.0.0.0 等于给局域网开一条不经认证的通道，防火墙也拦不住
（共享通道至少有 UAC 加规则的门槛）。

### 2.3 分流与故障切换

- **最少连接优先，同负载轮询**：每个新 TCP 连接选择健康且连接较少的上游。拨号中的连接也占位，
  选择与占位在锁内完成；已有连接固定使用原上游，结束后释放占位。切预设保留存量连接的负载。
- **故障切换**：`create_connection(timeout=3)` 失败 → 立即试下一台；全部失败才掐客户端
  （V1 是直接掐，proxy_tool.py:453-455，此处顺带修复）
- **失败降级**：首次失败后 1 秒内不作首选，连续失败 ≥3 次则降级 30 秒；仍可兜底。
  已知失败节点同时最多一个恢复探测，成功即恢复；只影响新连接。

### 2.4 已接受的代价（不再讨论）

- 工具未运行/崩溃 = 全机断网（系统代理指向无人监听的端口）
- 开机到自启工具就绪前有几秒断网窗口
- 7890 若被 Clash 等占用需在设置里改端口（入口端口可配，默认 7890）

## 八、2026-10-26 性能与稳定性验证

### 本次改动

- 本机多上游入口按健康状态、连接负载选择，慢节点积压时让其他节点承接新连接。
- 连接数包括拨号中、已建立和空闲长连接；不是带宽测速，也不会迁移已有 HTTP/2、CONNECT 隧道。
- 三个入口共用 256 个会话槽位（常量 `MAX_FORWARD_CONNECTIONS`）。达到上限时关闭新增连接，
  已建立的连接继续工作；释放后可接入。这样将转发线程限制在约 512 个以内，避免无限增长。
- Windows TCP 保活：空闲 60 秒后探测，间隔 10 秒。由 TCP 判断对端是否失联，
  不给正常空闲连接加 3 秒读超时；不支持的 socket 选项独立回退。
- 线程创建失败、停止期间的待处理客户端、拨号失败、切预设及 socket 关闭异常均有资源释放路径。
- 保留 64 KiB 单方向复用缓冲区。64/256 KiB 对比未显示稳定普遍收益，不单纯加大缓冲区。

### 对比结果（三轮中位数）

基线为本轮修改前 `proxy_tool.py.before-throughput-optimization.bak`，已包含前两轮优化。
测试均使用本机回环网络、独立 V2 进程及两份未经修改的 `lan-forward-proxy` 代码。

**不等速链路模拟：** 在两上游前分别施加共享下行限速 2/8 MiB/s；8 路并发、64 个新 TCP 连接，
每个下载 256 KiB。每个响应的全部字节校验通过，三轮均无请求错误。

| 指标 | 本轮修改前 | 本轮修改后 |
|---|---:|---:|
| 总吞吐 | 4.01 MiB/s | 7.62 MiB/s |
| 完成耗时 | 3.995 秒 | 2.101 秒 |
| 请求 P95 耗时 | 873 毫秒 | 606 毫秒 |

此模拟场景吞吐约提升 90%，耗时约减少 47%。这是有利于按连接分流的合成负载，
不是用户的外网测速；持久连接的流量不会在建立后重新分配，实际改善取决于应用连接方式、上游差异及本机带宽。

**不限速本地链路：** HTTP keep-alive、每轮 64 个 8 MiB 响应。吞吐中位数如下，
不同并发下约 -2% 到 +3%，未看到普遍的大文件提速。1 KiB 小请求与全部大文件响应长度检查通过。

| 并发 | 修改前 MiB/s | 修改后 MiB/s |
|---|---:|---:|
| 1 | 514.61 | 510.36 |
| 16 | 561.08 | 578.41 |
| 64 | 562.74 | 552.06 |

结果文件：`benchmark-balance-results.json`、`benchmark-results.json`；缓冲区探索数据见 `benchmark-tuning.json`。
本地测试受系统调度、运行顺序和缓存影响，三轮不足以证明小幅差异；不把不限速结果作为普遍提速承诺。

## 九、2026-10-26 连通性测试修正

旧测试仅请求 `http://www.gstatic.com/generate_204`，单次 I/O 超时 3 秒。
它和浏览器访问 Google 的 HTTPS 路径不同；站点故障、HTTP 被拦、超时，以及池中部分上游失败，
都可能导致测试失败但浏览器仍能访问。多代理列表此前把 HTTP/证书等错误简化成“失败”，无法进一步判断。

现在测试逐台显式连接所选上游的 HTTP 端口，通过 CONNECT 建立 HTTPS 隧道，先请求
`https://www.google.com/generate_204`，失败再请求 `https://www.gstatic.com/generate_204`。
单次 I/O 超时改为 6 秒，转发拨号仍为 3 秒。证书必须有效、站点必须返回预期 204；不关闭证书验证，
不因收到登录页/拦截页的 200 响应就认定成功，也不受本机 PAC、代理绕过列表或 NO_PROXY 干扰。
测试后关闭响应与连接，不改动上游池健康状态。

界面增加“详情”，按上游列出两个站点的失败原因。列表显示 HTTP 状态、证书错误、隧道拒绝、
协议错误等分类；部分节点失败时显示通过数量，不把单节点失败描述为整个代理不可用。
成功耗时包括 CONNECT/TLS 与站点响应，不是纯网络 ping 延迟，也不表示整段网页加载速度。

本轮 86 项 Python 非界面测试与 1 项真实代理集成测试通过。原有 25 项界面测试仍受 Tcl 环境故障影响。
尚未复现目标电脑的原始故障，更新后需以“详情”中的具体错误继续定位。
仅需再次复制 `proxy_tool.py`，退出目标电脑旧进程、覆盖并重新启动；修改前备份为
`proxy_tool.py.before-connectivity-fix.bak`。

### 核心修复与统计

1. 三个监听入口创建 accept 线程失败时，会关闭监听 socket、恢复停止状态，不再留下占用但无人服务的端口。
2. SOCKS CONNECT 首包转发遇客户端断开时，确保上游 socket 关闭。
3. 严格校验 CONNECT 的 HTTP 版本与状态码，避免错误响应文本含“200”就误判成功。
4. SOCKS 客户端握手、上游 CONNECT 分别使用完整 I/O 截止预算，防止慢速分包不断续期占用并发槽位。
   成功建立的隧道仍取消读超时。此预算不代表对系统 DNS 阻塞的绝对硬截止。
5. 小于 256 KiB 且保持连接的流量也纳入快照：每管道发布 sent/accounted 计数，
   界面刷新时叠加尚未入账的差值。累计提交仍按 256 KiB 批次执行，交接与快照使用同一把锁，
   不新增逐块争抢全局锁，也不双算；停止/异常时清除管道记录。

## 十二、2026-10-26 后台健康检测、故障日志与上游管理

### 后台 HTTPS 健康检测

- 程序启动后检测当前预设中启用的上游，每台完成检测后约 30 秒再次检测；最多两个后台工作线程，
  不随节点数量创建线程，不在 Tk 主线程等待网络。
- 沿用显式 CONNECT + TLS + 204 检测，一个目标失败后复查另一目标。列表显示正常延时、待复查、
  降级、恢复中；上游配置标题显示汇总，点击“详情”可分别查看 HTTPS 与 TCP 拨号状态。
- 连续 3 次完整检测失败降低新连接分配优先级；降级后连续 2 次成功恢复。
  TCP 端口能连接不会清除 HTTPS 降级。检测延时包含隧道、TLS 与响应，不是带宽测速。
- 全部节点都降级时仍允许兜底转发，避免检测站点共同故障让整个代理池停用。
  已经建立的连接继续使用原上游；该上游断线时仍需客户端重新连接，不能无缝迁移已有隧道。
- 修改备注保留健康状态；地址变化、停用、切换预设及退出后的迟到结果不得污染当前状态。
  手动“测试连通”结果单独展示，不直接修改后台的连续失败计数。

## 十四、2026-10-30 上下游稳定性调整

这次同时修改 V2 与 `lan-forward-proxy`，保留标准库、外部 assets、已有配置格式。

- 防自循环：保存、启动时拦截指向本工具监听端口的本机地址；实际拨号前也检查
  DNS 解析结果，覆盖别名和热切换。其他电脑的同端口、其他本机代理端口仍可使用。
- 本机入口选择上游的总预算为 6 秒，每台上游最多 3 秒，包含 DNS 与多个解析地址。
  超过预算终止本次连接，后续连接继续按健康/负载选择；不会在已发送业务数据后重放请求。
- DNS 使用 2 个固定后台线程、16 项等待队列；同一个地址并发解析合并，成功结果缓存
  10 秒，最多 128 项。拨号全部失败立即清掉该缓存。系统 DNS 本身不可取消，调用方
  仍按预算返回；滞留解析的线程和队列数量受限。
- SOCKS5 桥接的局域网拨号仍最多 3 秒；收到上游 CONNECT 响应另有 35 秒总预算，
  给上游默认 30 秒外网建连留出余量。碎片响应不会重置预算，成功后的隧道不设空闲读超时。
  如果手工修改上游外网建连超时，应同步调整 V2 的 `UPSTREAM_CONNECT_TIMEOUT_SECS`。
- 三入口合计仍最多 256 个连接；共享 HTTP/SOCKS 合计最多 192 个，为本机入口保留
  64 个名额；每个共享客户端 IP 最多 96 个。达到上限拒绝新连接，已有传输不被挤掉。
- 监听异常后按 0.25/1/2 秒有限重试，每 60 秒最多重建 3 次；保留已接通的隧道。
  点击停止会取消恢复任务。恢复中/最终失败在界面显示，不再仅凭系统代理开关显示正常。
  最终失败可关闭再开启；运行时恢复不擅自更改系统代理设置。
- 上游增加跨协议连接上限、HTTP 总连接池上限、可取消的等待队列、建连截止时间、
  DNS 任务上限、轮转日志、有限自动重启与有时限的连接排空。参数详见上游 README。
