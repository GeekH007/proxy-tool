## 一、目标与范围

**第一阶段（本次实现）：**

- 本机 HTTP 代理入口（透明转发、零协议解析），系统代理改指向它
- 上游池：多个上游、按**连接**轮询分流
- 故障切换：拨号失败顺延下一台，全挂才断客户端；简单熔断
- 统计按上游分列：状态行显示每台 连接数/速率
- 测试按钮对池内每台上游单独测

**非目标（第一阶段明确不做）：**

- 局域网共享接池（共享继续跟"池中第一台"走，行为等价 V1，不改坏）
- 单连接提速（多路分片下载）
- SOCKS5 上游（透明转发只认 HTTP 上游；91 若是别的协议再说）

## 二、核心设计（含两处修正）

### 2.1 入口 = 透明转发，不解析协议

初稿"只做 CONNECT"是错的：明文 `http://` 请求（绝对 URI 的 GET）不走 CONNECT，会漏。
正确做法更简单：**入口不解任何协议**——客户端连上入口后无论发 CONNECT 还是 GET，
字节原样转给选中的上游（上游本来就是 HTTP 代理，什么都认识）。
即 `HttpServer` ≈ `RelayServer` 克隆 + 上游池选择器，实现量比重写桥接更小。

### 2.2 监听地址：必须绑 127.0.0.1

RelayServer/SocksServer 绑 `0.0.0.0` 因为要给局域网用。入口只服务本机，
**绑 127.0.0.1**——绑 0.0.0.0 等于给局域网开一条不经认证的通道，防火墙也拦不住
（共享通道至少有 UAC 加规则的门槛）。

### 2.3 分流与故障切换

- **round-robin 按连接**：每个新 TCP 连接取下一个上游；同连接所有字节走同一条链路。
  批量下载/多线程分片天然摊开
- **故障切换**：`create_connection(timeout=5)` 失败 → 立即试下一台；全部失败才掐客户端
  （V1 是直接掐，proxy_tool.py:453-455，此处顺带修复）
- **简单熔断**：连续失败 ≥3 次的上游 30 秒内不作为首选（仍可作兜底被试到）

### 2.4 已接受的代价（不再讨论）

- 工具未运行/崩溃 = 全机断网（系统代理指向无人监听的端口）
- 开机到自启工具就绪前有几秒断网窗口
- 7890 若被 Clash 等占用需在设置里改端口（入口端口可配，默认 7890）

## 三、UI 与配置（替用户定的默认，实现时可调）

- **预设语义升级**：一个预设 = 一组上游（旧 `{ip,port}` 自动迁移为单元素组）
- 主界面：预设下拉保留；IP/端口输入框 + 「添加」入池；池以小 Listbox 呈现，
  选中可「删除」；替代现在的单值编辑
- **开关代理 = 起/停入口 + 系统代理指向 `127.0.0.1:入口端口`**
- 状态行：`✓ 代理中（2 上游）｜ 73: 3连接 ↓1.2MB/s ｜ 91: 1连接 ↓300KB/s`
- 测试按钮：逐台 generate_204，分列显示结果
- settings 新增 `entry_port`（默认 7890）
- **共享兼容**：RelayServer/SocksServer 上游跟随池中第一台（`_read_upstream`
  返回池[0]，其余逻辑不动）

## 四、验收标准

1. 池中 2 台时批量下载 ≥ 单台的 1.6 倍（91 配好后实测；仅 73 在池时先验证功能不回归）
2. 拔掉一台（改错端口模拟），浏览器不中断——故障切换生效
3. 旧配置文件启动自动迁移，单上游行为与 V1 无差别
4. 共享通道（手机走 7891/7892）行为与 V1 一致
